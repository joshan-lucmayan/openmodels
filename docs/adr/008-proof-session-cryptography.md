# ADR 008 — Proof-Session Cryptography and Design

- **Status**: Accepted
- **Date**: 2026-08-29

## Context

The show-once proof-key system requires a credential that:
- Is generated by a CSPRNG
- Is displayed exactly once and never persisted
- Is stored only as a cryptographic hash
- Supports validation (hashed comparison) in a deterministic, auditable way

The correct cryptographic choice depends on the nature of the secret.

## Cryptographic Choice

**Decision**: Use `secrets.token_hex(32)` (256-bit random) for key generation and
`SHA-256` for hashing.

**Key format**: `omk_<session_id_16hex>_<secret_64hex>`

### Rationale

1. **Key generation**: `secrets.token_hex(32)` produces 256 bits of
   cryptographically secure random data, sourced from the OS CSPRNG
   (`/dev/urandom`). 256 bits provides a 128-bit security level against
   brute-force — standard for API-key generation.

2. **Hashing choice**: For high-entropy (256-bit) CSPRNG-generated secrets,
   **SHA-256 is the appropriate, correct choice**. This is consistent with
   NIST SP 800-107 guidance for hashing high-entropy tokens and matches the
   practice of major API-key systems (GitHub, Stripe, etc. all store
   SHA-256 hashes of their API tokens).

3. **Why NOT a slow KDF**: bcrypt, scrypt, and argon2 are designed for
   **low-entropy passwords** (human-memorable, typically 20-40 bits of
   entropy). Applying a slow KDF to a 256-bit CSPRNG output adds no security
   benefit — the input already has full cryptographic entropy. The only
   effect would be unnecessary CPU cost on every verification. A slow KDF
   would be a *mistake* here.

4. **Why NOT HMAC**: HMAC-SHA256 with a server-side key would provide domain
   separation and protection against a hash-DB compromise where the pepper
   is stored separately. However, the session ID is stored in the clear and
   the secret is 256-bit random — without a separate pepper key, HMAC
   provides no benefit over plain SHA-256. A future version MAY add a
   pepper via HMAC if the deployment model requires it.

## Show-Once Pattern

The raw key is:
- Constructed in memory only (`raw_key = f"omk_{session_id}_{secret}"`)
- Returned exactly once in the `ProofSessionResult` object
- Never written to the database (only `SHA-256(raw_key)` is stored)
- Never written to logs, stdout (after creation), stderr, exceptions, or
  audit records

The `ProofSessionResult` is the ONLY object that ever carries the raw key.
It must be rendered once by the CLI and then discarded.

## Masked Reads

All commands that inspect or list existing proof sessions return a masked
representation:
- The masked key is `omk_<session_id>...` — the session id IS the key
  identifier, so the mask reveals it while hiding the secret entirely
- The stored `key_hash` is additionally truncated to 8 hex chars + "..."
- The `username` is metadata (not a secret) and is returned in full
- The raw key is NEVER returned by any read/list command

## Validation Pipeline

Presented key → parse (split on `_`) → lookup session by ID → SHA-256 hash
and compare → check revocation → check expiration → check target binding →
check finding binding → check actor binding → record usage → attach
authentication evidence to the finding → authenticate.

Revocation is checked before expiry so a revoked session can never be
re-classified as expired (revocation is the stronger, persistent state).

## Lifetime

- Default: 24 hours
- Configurable per creation
- Immediate revocation supported
- Historical record preserved after revocation

## Security Boundary

The proof key authenticates ONLY against the **authorized test target** for
the affected actor. It is NOT a privileged credential and does NOT grant
administrator access. It must NEVER be used against production or third-party
systems.

## Rejected Alternatives

| Approach | Rejected because |
|---|---|
| bcrypt/argon2 for hashing | Unnecessary for high-entropy secrets; adds CPU cost without benefit. |
| HMAC with pepper | Future option; no benefit without separate pepper management. |
| Store raw key in DB | Explicitly violates the show-once requirement. |
| Display key in multiple commands | Show-once pattern; only `finding prove` shows the raw key. |
| Key as CLI argument | Exposes to shell history; `--stdin` and getpass are safer. |
