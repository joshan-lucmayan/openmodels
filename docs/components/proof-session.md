# Proof Session System

**Module**: `opensystem/proof/`, `opensystem/impact/`

## Responsibility

The show-once attack-proof credential system. Generates a short-lived,
single-display, strictly-scoped credential for the authorized test target
after a confirmed finding has been independently impact-verified.

## Component Relationships

```
Finding (CONFIRMED) → ImpactVerifier → ImpactVerification
         ↓
Finding (CONFIRMED + verified) → ProofSessionService.create()
         ↓
ProofSessionResult (raw key shown once) → CLI → Researcher
         ↓
ProofSessionService.verify(raw_key) → full validation pipeline
         ↓
CaseStudy (assembled from store; never contains raw key)
```

## Key Security Properties

- Key generated by CSPRNG (256-bit entropy via `secrets.token_hex(32)`)
- Only SHA-256 hash stored in the database
- Raw key displayed exactly once at creation
- Validation pipeline: parse → lookup → hash-compare → revocation →
  expiry → target binding → finding binding → actor binding →
  authenticate + record usage + attach evidence to the finding
- Revocation takes precedence over expiry: a revoked session is never
  re-classified as expired, and `revoked_at` is persisted
- Masked reads: inspect/list commands return the masked key
  (`omk_<session_id>...`) and a truncated hash only; the raw key is never
  returned
- No raw key leakage to: stdout (after creation), stderr, logs, DB,
  exceptions, case studies, exports

## Cryptographic Choice

SHA-256 for high-entropy CSPRNG tokens (see ADR 008). Key format:
`omk_<session_id>_<64hex_secret>`. No slow KDF (unnecessary for
256-bit secrets).

## Required Gating

A proof session may only be created when ALL of the following pass:

1. Finding status is CONFIRMED
2. ImpactVerifier has independently confirmed the resource was reached
3. Target adapter explicitly supports proof sessions
4. Policy permits PROOF_SESSION operation
5. The affected actor and resource are resolvable

The resolved actor and resource records are persisted at creation time so
the binding is auditable from the store.

## Secret Handling in the CLI

`proof-key verify` deliberately does NOT accept the raw key as an argument:
arguments are recorded in shell history and process listings. The key is
read from stdin (`--stdin`) or an interactive no-echo prompt (getpass),
never echoed, never logged, and never included in output or exceptions.

## CLI Commands

- `opensystem impact verify <finding-id>` — independent impact verification
- `opensystem finding prove <finding-id>` — create show-once proof key
- `opensystem proof-key inspect <session-id>` — masked read
- `opensystem proof-key list` — masked list
- `opensystem proof-key revoke <session-id>` — immediate revocation
- `opensystem proof-key verify --stdin` — validate key (no echo)
- `opensystem case-study create/show/export` — reproducible reports
